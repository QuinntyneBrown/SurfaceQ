# L2 - Detailed Requirements

## L2-001: `generate` subcommand writes public-api.ts
**Traces to:** L1-002

The `generate` subcommand shall run discovery and write (overwriting) the generated content to the resolved `entryFile` path.

**Acceptance Criteria:**
1. Given a valid Angular library with an `ng-package.json`, when the user runs `surfaceq generate`, then the tool must write the generated content to the path specified by `entryFile` and exit with code `0`.
2. Given an existing `public-api.ts`, when `generate` runs, then the file must be overwritten with the newly rendered content.
3. Given `--project <path>` pointing to a project directory, when `generate` runs, then the tool must resolve `ng-package.json` within that directory and operate against it.
4. Given `--project <path>` pointing directly to an `ng-package.json` file, when `generate` runs, then that manifest must be used.

---

## L2-002: `check` subcommand verifies drift
**Traces to:** L1-002, L1-006

The `check` subcommand shall compare the would-be generated output against the on-disk `public-api.ts` without writing, and exit non-zero on drift.

**Acceptance Criteria:**
1. Given the on-disk `public-api.ts` matches the generated output byte-for-byte, when `surfaceq check` runs, then the tool must exit with code `0` and must not modify the file.
2. Given the on-disk `public-api.ts` differs from the generated output, when `check` runs, then the tool must exit with code `1` and print a concise drift message to stdout without printing the full diff.
3. Given an error occurs during execution (missing manifest, parse failure, etc.), when `check` runs, then the tool must exit with code `2`.

---

## L2-003: `diff` subcommand prints unified diff
**Traces to:** L1-002

The `diff` subcommand shall emit a human-readable unified diff between the existing and would-be generated output without writing to disk.

**Acceptance Criteria:**
1. Given files match, when `surfaceq diff` runs, then the tool must exit with code `0` and print no diff.
2. Given files differ, when `diff` runs, then the tool must print a unified diff to stdout and exit with code `1`.
3. Given an execution error, when `diff` runs, then the tool must exit with code `2`.
4. Given any invocation of `diff`, when the command completes, then the on-disk `public-api.ts` must be unchanged.

---

## L2-004: Project locator walks upward for ng-package.json
**Traces to:** L1-003

The project locator shall search for `ng-package.json` starting at the working directory (or `--project` path) and walking toward the filesystem root.

**Acceptance Criteria:**
1. Given `ng-package.json` exists in the starting directory, when the locator runs, then it must resolve that file.
2. Given `ng-package.json` exists in an ancestor directory, when the locator runs from a nested subdirectory, then it must resolve the nearest ancestor's manifest.
3. Given no `ng-package.json` exists in the path to the filesystem root, when the locator runs, then the tool must exit with code `2` and log an error message identifying the search path.

---

## L2-005: entryFile resolution and fallback
**Traces to:** L1-003, L1-011

The `entryFile` field of `ng-package.json` (resolved relative to the manifest's directory) determines both the output path and the scan root.

**Acceptance Criteria:**
1. Given `ng-package.json` specifies `entryFile: "src/public-api.ts"`, when the tool resolves paths, then the output path must equal `<manifestDir>/src/public-api.ts` and the scan root must equal `<manifestDir>/src`.
2. Given `ng-package.json` does not contain an `entryFile` field, when the tool resolves paths, then it must fall back to `src/public-api.ts` and log an informational message.
3. Given `ng-package.json` is malformed JSON, when the tool runs, then it must exit with code `2` and log an error identifying the file and the parse error.
4. Given the resolved `entryFile` directory does not exist, when the tool runs, then it must exit with code `2` with a clear error message.

---

## L2-006: Source file walker exclusions
**Traces to:** L1-003

The source file walker shall recursively enumerate `.ts` files under the scan root, excluding `*.spec.ts`, `*.stories.ts`, any file literally named `index.ts`, the `entryFile` itself, and any file under a `node_modules` directory.

**Acceptance Criteria:**
1. Given a scan root containing a mix of `.ts`, `.spec.ts`, `.stories.ts`, and `index.ts` files, when the walker runs, then the returned list must include only non-excluded `.ts` files.
2. Given a scan root containing a `node_modules` subdirectory with `.ts` files, when the walker runs, then no file under `node_modules` must be returned.
3. Given a scan root that contains the `entryFile`, when the walker runs, then the `entryFile` itself must not be returned.
4. Given the scan root contains zero `.ts` files after exclusions, when `generate` runs, then an empty `public-api.ts` must be written, an informational message logged, and exit code `0` returned.

---

## L2-007: Deterministic file ordering
**Traces to:** L1-005

The walker shall sort discovered files by relative path in a deterministic, cross-platform order.

**Acceptance Criteria:**
1. Given the same set of input files, when the walker runs on Windows, Linux, and macOS, then the returned ordering must be identical.
2. Given the tool runs twice against unchanged source, when outputs are compared, then they must be byte-identical.

---

## L2-008: Symbol discovery categories
**Traces to:** L1-004

The discovery engine shall identify named exports across documented categories: Angular decorators (Component, Directive, Pipe, Injectable, NgModule), standalone primitives and functional guards/interceptors/resolvers, type aliases, interfaces, enums and const enums, exported const/let/var including `InjectionToken` instances, exported functions and classes, file-level `export { X } from '...'` re-exports, and type-only exports.

**Acceptance Criteria:**
1. Given a file contains `export class FooComponent` decorated with `@Component`, when discovery runs, then `FooComponent` must appear as a value export.
2. Given a file contains `export interface Bar`, when discovery runs, then `Bar` must appear as a type-only export.
3. Given a file contains `export type Baz = ...`, when discovery runs, then `Baz` must appear as a type-only export.
4. Given a file contains `export const TOKEN = new InjectionToken<...>()`, when discovery runs, then `TOKEN` must appear as a value export.
5. Given a file contains `export { X } from './sub'`, when discovery runs, then `X` must be emitted in the generated output with the correct re-exported form.
6. Given a file contains `export type { Foo }`, when discovery runs, then `Foo` must be emitted as a type-only export.

---

## L2-009: Wildcard re-export expansion
**Traces to:** L1-001, L1-004

Files containing `export *` wildcard re-exports shall be resolved through the TypeScript Compiler API into the underlying named symbols and emitted explicitly in the generated output.

**Acceptance Criteria:**
1. Given a file contains `export * from './inner'` where `./inner` exports `A` and `B`, when the tool runs, then the generated output must emit `A` and `B` as named exports (via the file that originally contained them) with no wildcard form.
2. Given output is inspected, when searched for `export *`, then no occurrence must be present.

---

## L2-010: Default export skip with warning
**Traces to:** L1-011

Default exports shall be skipped and a warning logged to stderr; the run must continue and exit `0`.

**Acceptance Criteria:**
1. Given a file contains `export default ...`, when the tool runs, then no default export must appear in the generated output.
2. Given a default export is skipped, when the tool runs, then a warning prefixed `warn:` identifying the offending file (as a relative path) must be written to stderr.
3. Given only default exports exist in a file, when the tool runs, then the overall exit code must still be `0`.

---

## L2-011: Output format structure
**Traces to:** L1-005

The generated file shall not include generated/regenerate header comments. It shall group symbols from the same source file into one `export { ... } from '...'` statement, emit files in discovered order, preserve source-order within a file, use relative POSIX-style module specifiers without a `.ts` extension, and end with a trailing newline when non-empty. Indentation shall use two spaces.

**Acceptance Criteria:**
1. Given any generation run, when the output is inspected, then it must not contain generated/regenerate header comments.
2. Given a file exports `A`, `B`, and `C` as values, when the tool renders, then a single `export { A, B, C } from '<relative>'` statement must be emitted.
3. Given files are processed on Windows, when module specifiers are inspected, then they must use forward slashes and must not contain backslashes.
4. Given any emitted module specifier, when inspected, then it must not contain a `.ts` suffix and must be a relative path from the entry file's directory.
5. Given any non-empty generated file, when inspected byte-for-byte, then it must end with a single trailing newline.
6. Given a file exports both a value `X` and a type `Y`, when rendered, then two adjacent statements `export { X } from '...'` and `export type { Y } from '...'` must be emitted.
7. Given indentation is inspected inside multi-line statements, then two-space indentation must be used.

---

## L2-012: Determinism across runs and platforms
**Traces to:** L1-005, L1-006

Output must be byte-identical across runs, hosts, and operating systems for unchanged input.

**Acceptance Criteria:**
1. Given the same fixture library, when the tool runs sequentially on Windows, Linux, and macOS CI agents, then the resulting `public-api.ts` files must hash identically (SHA-256).
2. Given any two successive runs against unchanged source on the same host, when outputs are diffed, then they must be byte-identical.

---

## L2-013: Node.js sidecar lifecycle and communication
**Traces to:** L1-004, L1-010

The .NET host shall spawn a bundled Node.js sidecar process per CLI invocation, communicate via newline-delimited JSON on stdio, and pass only file paths (never file content) as parameters.

**Acceptance Criteria:**
1. Given a CLI invocation, when the tool starts, then exactly one Node sidecar process must be spawned with explicit arguments (no shell invocation).
2. Given the sidecar is launched, when its parameters are inspected, then the arguments and JSON payload must contain only file paths and a `projectRoot`, never file contents.
3. Given the CLI invocation completes, when processes are checked, then the sidecar process must be terminated.
4. Given the CLI sends a `discover` request, when the sidecar responds, then the response must include the `id` matching the request and a `result.files` array with per-file `exports` and `warnings`.

---

## L2-014: Bundled Node runtime and TypeScript package
**Traces to:** L1-007, L1-010

The NuGet package shall bundle Node.js binaries per runtime identifier (RID) and the `typescript` npm package pre-installed, requiring no `npm install` at runtime and no user-installed Node.js.

**Acceptance Criteria:**
1. Given a clean machine with no Node.js installed, when the user installs SurfaceQ via `dotnet tool install --global SurfaceQ` and runs `surfaceq generate`, then the command must succeed.
2. Given the installed package contents are inspected, when Node binaries are listed, then binaries must be present for Windows x64/ARM64, Linux x64/ARM64, and macOS x64/ARM64.
3. Given the installed package contents are inspected, when sidecar `node_modules` is listed, then `typescript` must be present and no `npm install` must be executed during any CLI run.
4. Given the installed package on disk, when measured, then the total footprint must be under 60 MB.

---

## L2-015: Cold and warm performance targets
**Traces to:** L1-008

The tool shall meet documented runtime performance targets on a modern developer laptop.

**Acceptance Criteria:**
1. Given a 50-file library and a cold tool invocation, when `surfaceq generate` runs, then it must complete in under 5 seconds.
2. Given a 200-file library, when `surfaceq generate` runs in a warm state, then it must complete in under 10 seconds.
3. Given a 500-file library, when the tool runs, then peak working set memory must remain under 512 MB.

---

## L2-016: Logging streams and verbosity
**Traces to:** L1-009

Logging shall be plain-text via `Microsoft.Extensions.Logging` with a console provider. A global `--verbosity <level>` flag shall accept `quiet`, `minimal`, `normal` (default), `detailed`, and `diagnostic`. Errors and warnings go to stderr; informational and verbose output go to stdout.

**Acceptance Criteria:**
1. Given any invocation, when log output is captured, then warnings and errors must be written to stderr and informational messages to stdout.
2. Given `--verbosity quiet`, when the tool runs without errors, then no output must be produced on stdout.
3. Given `--verbosity diagnostic`, when the tool runs, then detailed trace output including file discovery and sidecar communication must be produced.
4. Given no `--verbosity` flag is provided, when the tool runs, then `normal` verbosity must be used.
5. Given any log output, when inspected, then it must be plain text with no ANSI color codes and no JSON framing.

---

## L2-017: No network, no telemetry
**Traces to:** L1-010

The tool shall not perform any network I/O at runtime.

**Acceptance Criteria:**
1. Given any CLI invocation, when network traffic is monitored, then zero outbound connections must be observed from the SurfaceQ process or sidecar.
2. Given any invocation, when telemetry collection is audited, then no telemetry endpoint must be contacted and no update checks must be performed.

---

## L2-018: Syntax error handling
**Traces to:** L1-011

When the sidecar reports a syntax-error diagnostic, the tool shall exit with code `2` and report the offending file and line.

**Acceptance Criteria:**
1. Given a scanned file contains a TypeScript syntax error, when the tool runs, then it must exit with code `2` and print an error to stderr identifying the file (as a relative path) and line number.

---

## L2-019: File permission errors
**Traces to:** L1-011

When the target `public-api.ts` cannot be written due to filesystem permissions, the tool shall exit with code `2` and report a permissions error.

**Acceptance Criteria:**
1. Given `public-api.ts` exists and is read-only, when `surfaceq generate` runs, then it must exit with code `2` and print an error to stderr identifying the file and the permission issue.

---

## L2-020: Name collisions are not adjudicated
**Traces to:** L1-001, L1-011

When the same exported name originates from two different files, both shall be emitted; SurfaceQ shall not rename or omit either.

**Acceptance Criteria:**
1. Given two scanned files both export a symbol named `Foo`, when the tool runs, then both `export { Foo } from '...A'` and `export { Foo } from '...B'` statements must be present in the output.

---

## L2-021: Global flags surface
**Traces to:** L1-002

The CLI shall expose global `--verbosity`, `--version`, and `--help` / `-h` flags alongside every subcommand.

**Acceptance Criteria:**
1. Given `surfaceq --version`, when executed, then the SurfaceQ semantic version must be printed to stdout and the process must exit with code `0`.
2. Given `surfaceq --help` or `surfaceq -h`, when executed, then help text listing all subcommands and global options must be printed and exit with code `0`.
3. Given `surfaceq <subcommand> --help`, when executed, then subcommand-specific help must be printed and exit with code `0`.

---

## L2-022: No v1 configuration file
**Traces to:** L1-012

v1 shall not read any project-level configuration file; all behavior is driven by `ng-package.json` plus CLI flags.

**Acceptance Criteria:**
1. Given any file named `surfaceq.config.json`, `.surfaceqrc`, or similar is present in the project, when the tool runs, then it must be ignored and behavior must be identical to a run without those files.

## L2-023: `docs` subcommand documents every workspace library
**Traces to:** L1-002, L1-013

The `docs` subcommand shall locate every `ng-package.json` under the workspace path (excluding `node_modules` and `dist`), and write one Markdown document per library next to its manifest. The library title shall be taken from the sibling `package.json` `name`, falling back to the library directory name.

**Acceptance Criteria:**
1. Given a workspace containing two libraries, when `surfaceq docs --project <ws>` runs, then a Markdown file (default `API.md`) must be written into each library directory and the tool must exit with code `0`.
2. Given a library with a `package.json` declaring `name`, when `docs` runs, then the document title must use that name.
3. Given a `node_modules` or `dist` directory containing an `ng-package.json`, when `docs` runs, then that directory must not be treated as a library.

---

## L2-024: Interfaces, functions, and classes document members
**Traces to:** L1-013

The generated Markdown shall render each interface (and class) with tables of its properties (name, type, optionality, readonly) and methods (name, parameters, return type), and shall render functions with their parameters and return type. Member detail is sourced from the TypeScript AST via the sidecar `document` method.

**Acceptance Criteria:**
1. Given an exported interface with properties and methods, when `docs` runs, then the document must list each property's type and each method's parameters and return type.
2. Given a `readonly` or optional property, when `docs` runs, then the document must indicate the modifier.

---

## L2-025: Injection tokens document their contract type
**Traces to:** L1-013

For each `export const X = new InjectionToken<T>('…')`, the generated Markdown shall list the token and its contract type `T` so consumers know which interface to depend on.

**Acceptance Criteria:**
1. Given an exported `InjectionToken<AuthService>`, when `docs` runs, then the Injection Tokens table must list the token name with contract type `AuthService`.

---

## L2-026: Documentation is deterministic and table-safe
**Traces to:** L1-005, L1-013

The generated Markdown shall be byte-identical across repeated runs: declarations are ordered by name within each kind. Pipe characters in type text shall be escaped so they never break a Markdown table cell.

**Acceptance Criteria:**
1. Given an unchanged workspace, when `docs` runs twice, then both runs must produce byte-identical Markdown.
2. Given a type containing a `|` (e.g. a union type), when rendered into a table cell, then the pipe must be escaped as `\|`.

---

## L2-027: `--output` overrides the per-library document path
**Traces to:** L1-002, L1-013

The `docs` subcommand shall accept `--output <path>`, interpreted relative to each library directory, defaulting to `API.md`.

**Acceptance Criteria:**
1. Given `--output docs/PUBLIC_API.md`, when `docs` runs, then each library's document must be written to `<library>/docs/PUBLIC_API.md` (creating directories as needed).

---

## L2-028: Empty workspace exits with an error
**Traces to:** L1-011, L1-013

When no library is found under the workspace path, the `docs` subcommand shall exit with code `2` and report the searched path.

**Acceptance Criteria:**
1. Given a workspace path containing no `ng-package.json`, when `docs` runs, then the tool must exit with code `2` and print an error to stderr identifying the searched path.

---

## L2-029: Implementation classes are hidden by default
**Traces to:** L1-013

The `docs` document represents the contract consumers code against (exported interfaces + injection tokens). A class that implements an interface exported by the same library is an implementation reached via its token, so it shall be excluded from the document by default. Classes that implement only external interfaces, or no interface, shall remain. The `--include-implementations` flag overrides the exclusion.

**Acceptance Criteria:**
1. Given a library exporting interface `IThing` and class `Thing implements IThing`, when `docs` runs without flags, then the document must contain `IThing` but not `Thing`.
2. Given the same library, when `docs --include-implementations` runs, then the document must contain `Thing`.
3. Given a class that implements only a non-exported (external) interface or no interface, when `docs` runs, then that class must remain in the document.

---

## L2-030: Deprecation is surfaced
**Traces to:** L1-013

A declaration or member carrying a `@deprecated` JSDoc tag shall be marked deprecated in the generated Markdown via a callout for heading-rendered interfaces/classes/enums and a `Deprecations` summary table (rendered before `Contents` and linked from it whenever at least one item is deprecated); the tag's trailing text is shown as the reason, collapsed to one line and pipe-escaped. A per-row `Deprecated` column is **opt-in** via `--deprecated-column`: when enabled, every table gains the column showing the reason, `yes` for an empty reason, or `no` for a non-deprecated item; when omitted (the default), no table carries the column while the callout and summary still render.

**Acceptance Criteria:**
1. Given a type declared with `/** @deprecated Use X */`, when `docs --deprecated-column` runs, then its row's `Deprecated` column must show `Use X`.
2. Given a non-deprecated declaration, when `docs --deprecated-column` runs, then its `Deprecated` column must show `no`.
3. Given a deprecated interface, class, or enum, when `docs` runs, then a `> ⚠️ **Deprecated**` callout must appear directly under its heading.
4. Given a deprecated member inside a non-deprecated parent, when `docs --deprecated-column` runs, then only that member's row must be flagged.
5. Given a library with at least one deprecated item, when `docs` runs, then a `Deprecations` summary table must appear before `Contents` and be linked from it; given none, neither must appear.
6. Given identical inputs, when `docs` runs twice, then the output must be byte-identical.
7. Given a library with a deprecated item, when `docs` runs without `--deprecated-column`, then no table must contain a `Deprecated` column header while the callout and `Deprecations` summary must still render.

---

## L2-031: `inventory` subcommand writes one INVENTORY.md per project
**Traces to:** L1-002, L1-013

The `inventory` subcommand shall produce a complete census of developer-authored objects for an Angular application, library, or workspace, and write one Markdown document per discovered project. The `--output <path>` value is interpreted relative to each project directory, defaulting to `INVENTORY.md`. All projects are attempted; the command exits `2` if any project fails, no project is found, or a document cannot be written, and `0` otherwise.

**Acceptance Criteria:**
1. Given a workspace containing one application and one library, when `surfaceq inventory --project <ws>` runs, then an `INVENTORY.md` must be written into each project directory and the tool must exit with code `0`.
2. Given `--output reports/INVENTORY.md`, when `inventory` runs, then each project's document must be written to `<project>/reports/INVENTORY.md` (creating directories as needed).
3. Given a `--project` path under which no application or library is discovered, when `inventory` runs, then the tool must exit with code `2` and print an error identifying the searched path.
4. Given identical inputs, when `inventory` runs twice, then each document must be byte-identical between runs.

---

## L2-032: Project discovery spans applications and libraries
**Traces to:** L1-003, L1-013

Inventory project discovery shall find Angular **applications** and **libraries** under the target path. Applications are resolved from `angular.json` (`projects[*]`, object- or string-valued) and Nx `project.json`; libraries from `ng-package.json`. Directories under `node_modules` or `dist`, and projects whose name ends with `-e2e`, shall be excluded. When no project is discovered, the target path itself shall be treated as a single application rooted at its `src` directory when present. Results are deduplicated by project directory and ordered deterministically.

**Acceptance Criteria:**
1. Given a workspace `angular.json` declaring an `application` and a `library` project, when discovery runs, then both must be returned with their respective source roots.
2. Given a library directory containing `ng-package.json` and no `angular.json`, when discovery runs from that directory, then it must be returned as a `library` whose source root is the entry-file directory.
3. Given an `ng-package.json` or `angular.json` under a `node_modules` or `dist` directory, when discovery runs, then that directory must not be treated as a project.
4. Given an application directory containing a `src` folder but no manifest, when discovery runs from that directory, then it must be returned as a single `application` rooted at `src`.

---

## L2-033: Inventory covers all declarations and classifies Angular roles
**Traces to:** L1-004, L1-013

The sidecar `inventory` method shall report every top-level declaration in a scanned file — classes, interfaces, enums, type aliases, functions, and variables (const/let/var) — whether or not it is exported, marking each with an `exported` flag. Each declaration shall carry a `role`: an Angular construct (Component, Directive, Pipe, Service, NgModule, Guard, Resolver, Interceptor) detected from decorators, class heritage, or functional types, or otherwise a friendly name for its TypeScript kind. `*.spec.ts`, `*.stories.ts`, `*.e2e-spec.ts`, and `*.d.ts` files shall be excluded from the walk.

**Acceptance Criteria:**
1. Given a file with both `export class A {}` and a non-exported `class B {}`, when `inventory` runs, then both must be reported with `exported` `true` and `false` respectively.
2. Given a class decorated `@Component`, `@Directive`, `@Pipe`, `@Injectable`, or `@NgModule`, when `inventory` runs, then its role must be Component, Directive, Pipe, Service, or NgModule respectively.
3. Given a functional guard (`const g: CanActivateFn = …`), resolver (`ResolveFn`), or interceptor (`HttpInterceptorFn`), or a class implementing `CanActivate`/`Resolve`/`HttpInterceptor`, when `inventory` runs, then its role must be Guard, Resolver, or Interceptor.
4. Given an `export const T = new InjectionToken<X>('T')`, when `inventory` runs, then its role must be Injection Token and its kind `const`.
5. Given a `*.spec.ts` file, when the walker runs, then no declaration from it must be inventoried.

---

## L2-034: Inventory Markdown is deterministic and table-safe
**Traces to:** L1-005, L1-013

The generated inventory document shall begin with a title, then a `Summary` section reporting total/exported/internal counts and a per-category count table, then one section per non-empty category (in a fixed order) containing a table of `Name`, `Kind`, `Exported`, `File`, and `Description`. File paths shall be project-relative and POSIX-formatted. Output shall be byte-identical across runs (rows sorted by name then file within each category), pipe characters escaped, with LF endings and a single trailing newline. A project with no declarations shall render an explicit "no objects" line.

**Acceptance Criteria:**
1. Given a project with declarations across several categories, when rendered, then a `Summary` section and one `##` section per non-empty category (in the fixed order) must be present.
2. Given two declarations whose types or paths contain `|`, when rendered into a table cell, then each pipe must be escaped as `\|`.
3. Given identical input, when rendered twice, then the output must be byte-identical.
4. Given a project with zero developer-authored declarations, when rendered, then the document must contain an explicit "no objects" line rather than empty tables.

---

## L2-040: `providers` generates an Angular provide-<project>.ts
**Traces to:** L1-004, L1-015

The `providers` subcommand shall, for every library under the workspace path, generate a `provide-<project>.ts` (project = the library directory name). For each `InjectionToken<T>` discovered in the project: when `T` is an interface implemented by an exported class, bind the token to that class with `useExisting`; otherwise treat `T` as a configuration value and bind it with `useValue` from a generated `Provide<Project>Options` field (field name = camelCase of the token, type = `T`). The file is written at the common-ancestor directory of the wired declarations with correct relative, POSIX, `.ts`-less import specifiers, plus the `@angular/core` import of `EnvironmentProviders`/`makeEnvironmentProviders`. Output is deterministic (tokens ordered by name, imports grouped and sorted), LF-terminated, UTF-8 without BOM. A token whose interface has no implementation is reported as a warning and skipped. A library with no injectable contracts is skipped. (A future revision will honor `@internal` / `@publicApi` JSDoc tags; v1 includes every implemented contract.) The command exits `2` when no library is found, a source fails to parse, or a file cannot be written, and `0` otherwise.

**Acceptance Criteria:**
1. Given a library with `export const FOO_SERVICE = new InjectionToken<IFooService>(...)` and `export class FooService implements IFooService`, when `providers` runs, then `provide-<project>.ts` must contain `{ provide: FOO_SERVICE, useExisting: FooService }` and an `import` of both symbols by relative path.
2. Given a config token `export const API_BASE_URL = new InjectionToken<string>(...)`, when `providers` runs, then the file must declare `Provide<Project>Options` with `readonly apiBaseUrl: string` and bind `{ provide: API_BASE_URL, useValue: options.apiBaseUrl }`; when no config token exists, the function must take no parameters and emit no options interface.
3. Given a token whose interface has no implementing class, when `providers` runs, then a `warn:` message must identify the token and the binding must be omitted.
4. Given a library with no injection tokens, when `providers` runs, then no `provide-*.ts` is written and the library is skipped with an informational message; given identical input, two runs must produce a byte-identical file.

---

## L2-041: `providers --folder` generates a single provide-<folder>.ts
**Traces to:** L1-004, L1-015

The `providers` subcommand shall additionally accept a `--folder <dir>` option that, instead of scanning a workspace for `ng-package.json` libraries, treats the given directory as a self-contained scan root: it walks that folder and all subfolders for `.ts` sources (excluding `node_modules`, `index.ts`, `*.spec.ts`, `*.stories.ts`) and generates a single `provide-<folder>.ts` (folder = the directory's own name) written at the folder root. The wiring rules, import formatting, determinism, warnings, and skip-when-no-contracts behavior are identical to the workspace mode (L2-040); only the discovery scope (one explicit folder vs. every library) and the output anchor (the folder root vs. the wired declarations' common ancestor) differ. When `--folder` is supplied it takes precedence over `--project`. The command exits `2` when the folder does not exist or a source fails to parse, and `0` otherwise — including when the folder holds no injectable contracts, which is reported informationally.

**Acceptance Criteria:**
1. Given a folder (with no `ng-package.json`) containing an injection token and its implementing class in a subfolder, when `surfaceq providers --folder <dir>` runs, then `<dir>/provide-<dir>.ts` must be written with a `{ provide: …, useExisting: … }` binding and a relative import of both symbols, and the tool must exit `0`.
2. Given a config token nested two levels below the folder, when folder mode runs, then its `useValue` binding and `Provide<Folder>Options` field must appear (subfolders are scanned recursively).
3. Given a folder path that does not exist, when folder mode runs, then the tool must exit `2` and print an error.
4. Given identical input, two folder-mode runs must produce a byte-identical file; given a folder with no injection tokens, no file is written and an informational message is printed with exit `0`.

## L2-042: `docs --services` documents the service contract surface
**Traces to:** L1-013

The `docs` subcommand shall accept a `--services` flag that restricts each generated document to the library's **service contract surface** — the interfaces an `@Injectable` service implements, the models/types/enums those contracts are built from, and the injection tokens that wire them — rather than the concrete service classes. Concretely, only declarations whose kind is `interface`, `type`, `enum`, or `injection-token` are documented; every class (the services and any other implementation), function, and plain const is reached through a token and is excluded. When `--services` is set and `--output` is not supplied, the per-library document is named `SERVICE_API.md` rather than `API.md`; an explicit `--output` always takes precedence. The sidecar `document` method shall continue to report a `role` on each class declaration (parity with `inventory`), although the `--services` filter now keys off declaration kind, not role. Output remains deterministic and table-safe.

**Acceptance Criteria:**
1. Given a library with an `@Injectable` class `AuthService` implementing an exported interface `IAuthService`, supporting interfaces/type aliases/enums, an injection token, a plain class, and a `@Component` class, when `surfaceq docs --services` runs, then `SERVICE_API.md` (not `API.md`) must be written containing `IAuthService`, the supporting models/types/enums, and the injection token — and none of the classes (`AuthService`, the plain class, the component) — and the tool must exit `0`.
2. Given `--services --output docs/SERVICES.md`, when `docs` runs, then each library's services document must be written to `<library>/docs/SERVICES.md` (the explicit `--output` overrides the `SERVICE_API.md` default).
3. Given an `@Injectable` class that implements an interface exported by the same library, when `docs --services` runs, then the interface (the contract) must be documented and the class must be excluded.
4. Given the sidecar `document` method runs on an `@Injectable` class and a plain class, then the first must carry `role` `Service` and the second `role` `Class`.
5. Given a multi-section services document (interfaces, injection tokens, enums, type aliases), when it is rendered, then a `## Contents` table of contents must be emitted.

## L2-043: `docs` excludes deprecated declarations by default
**Traces to:** L1-013

The `docs` subcommand shall, by default, omit any declaration whose JSDoc carries an `@deprecated` tag (the whole interface, class, enum, type alias, function, const, or injection token) from the generated document. A `--include-deprecated-types` flag shall restore them, in which case the prior behavior holds (the declaration is rendered with its callout and `Deprecations` summary entry, plus the `Deprecated` column when `--deprecated-column` is also passed, per L2-030). The exclusion is declaration-level only: a `@deprecated` member inside a *non-deprecated* declaration is unaffected — it is still rendered and still flagged. This default applies to the `docs` command alone; the `providers` pipeline continues to include deprecated declarations.

**Acceptance Criteria:**
1. Given a library with a `@deprecated` interface and a non-deprecated interface, when `docs` runs without flags, then the document must contain the non-deprecated interface and must not contain the deprecated one.
2. Given the same library, when `docs --include-deprecated-types` runs, then the deprecated interface must appear with its callout and a `Deprecations` summary entry.
3. Given a non-deprecated declaration with a `@deprecated` member, when `docs` runs without flags, then the declaration must remain and that member must still be flagged deprecated.
4. Given a library whose only deprecated items are excluded declarations, when `docs` runs without flags, then no `Deprecations` summary section must be rendered.

## L2-044: Callable interfaces document their call signatures
**Traces to:** L1-013

A function exposed as a contract is commonly modeled as a **callable interface** — an interface whose body is one or more call signatures `(params): ReturnType` — paired with an `InjectionToken<T>`. The sidecar `document` method shall report each call signature as a member of kind `call` carrying its parameters and return type (it has no name); the `MarkdownRenderer` shall render these in a `Call signatures` table (`Parameters | Returns | Deprecated | Description`) under the interface's heading, ahead of any property and method tables. A callable interface must therefore no longer render `_No public members._`. Call signatures honor the same JSDoc/`@deprecated` handling as named members and preserve source order for overloads.

**Acceptance Criteria:**
1. Given `export interface FormatDate { (date: Date, format: string): string; }` and `export const FORMAT_DATE = new InjectionToken<FormatDate>('…')`, when `docs` runs, then the `FormatDate` section must contain a `Call signatures` table listing `date: Date, format: string` and return `string`, and must not say `_No public members._`.
2. Given the sidecar `document` method runs on a callable interface, then it must return a member with `memberKind` `call`, an empty `name`, the call's `parameters`, and its `returnType`.
3. Given a callable interface that also declares named properties or methods, when rendered, then the `Call signatures` table and the property/method tables must all appear.
4. Given identical input, when `docs` runs twice, then the output must be byte-identical (overloaded call signatures keep their source order).

## L2-045: `--only-public-api` restricts output to `@publicApi`-tagged declarations
**Traces to:** L1-016

The `generate`, `check`, and `diff` subcommands shall accept an `--only-public-api` flag. When set, the rendered `public-api.ts` content shall include only exports whose declaration carries the `@publicApi` JSDoc tag in its type-level (declaration-level) doc comment. Only a tag at the start of a JSDoc line counts (matching the `@deprecated` convention) — a prose mention of `@publicApi` does not tag a declaration. The filter is kind-agnostic: interfaces, type aliases, enums, classes, functions, constants, and injection tokens all participate. The tag is read at the declaration site: the sidecar `discover` method shall report a `publicApi` boolean per export, and for a named re-export (`export { X } from './x'`, including `export { X as Y }` renames and local `export { X }` clauses) it shall trace the name to its original declaration through intermediate indirection — chained named re-exports, `export *` barrels (`index.ts` targets included), and `import { X }` feeding a local `export { X }` clause — reading the tag where the declaration lives (`false` when the chain cannot be resolved; circular barrels terminate). A JSDoc block on a variable statement applies to every declarator it exports. Without the flag, output is unchanged. Filtered output honors every existing format and determinism contract; a project in which no export carries the tag renders empty output and exits `0`. All three subcommands report each excluded export as a trace line (visible at `--verbosity diagnostic`) so the omission is observable.

**Acceptance Criteria:**
1. Given a project with a `/** @publicApi */`-tagged interface and an untagged interface, when `surfaceq generate --only-public-api` runs, then `public-api.ts` must re-export only the tagged interface and the tool must exit `0`.
2. Given tagged declarations of every kind (interface, type alias, enum, class, function, const, injection token) alongside untagged ones, when `generate --only-public-api` runs, then exactly the tagged declarations of every kind must appear (values on `export { … }` lines, types on `export type { … }` lines).
3. Given the same project, when `generate` runs without the flag, then every export must appear exactly as before (the flag is opt-in and the default behavior is unchanged).
4. Given a barrel `export { X } from './x'` (or `export { X as Y } from './x'`) where `X`'s declaration in `x.ts` carries `@publicApi`, when `generate --only-public-api` runs, then that re-export must be preserved; given the declaration is untagged, it must be dropped. The same holds when the tagged declaration sits behind an intermediate re-export chain, an `export *` `index.ts` barrel, or an `import { X }` / `export { X }` pair.
5. Given an on-disk `public-api.ts` that matches the filtered output, when `check --only-public-api` runs, then the tool must exit `0`; when `check` runs without the flag against the same file, then it must exit `1` (drift), and `diff` behaves identically. Given an on-disk file that still contains an untagged export, when `check --only-public-api` (or `diff --only-public-api`) runs, then it must exit `1`.
6. Given a project in which no exported declaration carries `@publicApi`, when `generate --only-public-api` runs, then it must write empty output and exit `0`; given identical input, two filtered runs must produce byte-identical output.
7. Given `--verbosity diagnostic`, when `generate --only-public-api` excludes an export, then a `trace: only-public-api excluded …` line naming the export and its declaring file must be emitted.

## L2-046: `docs --folder` documents a single folder scope
**Traces to:** L1-013

The `docs` subcommand shall additionally accept a `--folder <dir>` option that, instead of scanning a workspace for `ng-package.json` libraries, treats the given directory as a self-contained scan root: it walks that folder and all subfolders for `.ts` sources (excluding `node_modules`, `index.ts`, `*.spec.ts`, `*.stories.ts`) and writes a single Markdown document at the folder root (default `API.md`, or `SERVICE_API.md` under `--services`, or the `--output` path relative to the folder). Every existing `docs` filter applies unchanged — `--include-implementations`, `--services`, and the default `@deprecated` exclusion (`--include-deprecated-types`) — so a folder containing only one service yields a document describing just that service's surface. Determinism and table-safety are identical to the workspace mode (L2-026); only the discovery scope (one explicit folder vs. every library) and the output anchor (the folder root vs. each library directory) differ. When `--folder` is supplied it takes precedence over `--project`. The command exits `2` when the folder does not exist or a source fails to parse, and `0` otherwise.

**Acceptance Criteria:**
1. Given a folder (with no `ng-package.json`) containing a single service contract — an interface, its injection token, and the implementing class — when `surfaceq docs --folder <dir>` runs, then `<dir>/API.md` must be written documenting that one surface (the interface and token), and the tool must exit `0`.
2. Given source files nested in subfolders, when folder mode runs, then their declarations must appear (subfolders are scanned recursively).
3. Given a folder path that does not exist, when folder mode runs, then the tool must exit `2` and print an error.
4. Given identical input, two folder-mode runs must produce a byte-identical document; the `--services`, `--include-implementations`, and `--include-deprecated-types` filters behave exactly as in workspace mode.

## L2-047: `docs` omits the table of contents by default
**Traces to:** L1-013

The `docs` subcommand shall omit the `## Contents` table of contents from each generated Markdown document by default, emitting it only when the user passes a `--contents` flag. When the flag is absent the document begins with its `# <name> — Public API` heading followed directly by the body sections (and the `## Deprecations` summary, when present) with no navigation list; when the flag is present the `## Contents` section is rendered exactly as before — listing each non-empty section, plus a `Deprecations` entry when deprecated declarations are shown. The flag applies identically in workspace and `--folder` mode, composes with every other `docs` filter, and does not affect determinism or table-safety (L2-026).

**Acceptance Criteria:**
1. Given a multi-section library, when `surfaceq docs` runs without `--contents`, then the written document must not contain a `## Contents` heading or any `- [Section](#anchor)` navigation entry, while the body sections (e.g. `## Interfaces`) are still rendered, and the tool must exit `0`.
2. Given the same library, when `surfaceq docs --contents` runs, then the document must contain the `## Contents` section listing each non-empty section (and a `Deprecations` entry when deprecated declarations are present).
3. The `--contents` flag behaves identically in `--folder` mode and composes with `--services`, `--include-implementations`, and `--include-deprecated-types`.
